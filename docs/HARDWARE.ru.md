# Что доступно для управления

Чем на этой платформе можно и нельзя управлять и что эти ручки делают на самом
деле. Все значения прочитаны с работающей машины; непроверенное помечено явно.

Платформа: ASUS Zenbook 14 UX3405MA, Intel Core Ultra 9 185H (22 потока,
до 4.8 ГГц), Pop!_OS с ядром 7.0.11 и десктопом COSMIC. Драйверы `asus_wmi` /
`asus_nb_wmi` / `asus_armoury`; ACPI `platform_profile` работает. По умолчанию
запущены `system76-power` и `thermald`; `power-profiles-daemon` не установлен.

## Чего нет

Зафиксировать это первым делом дешевле, чем выводить заново.

- **Ручного управления вентилятором нет.** `pwm1_enable` принимает только `2`
  (авто, управляет EC) и `0` (полная скорость). Узла со значением PWM нет,
  кривой вентилятора нет нигде:
  `/sys/class/firmware-attributes/asus-armoury/attributes/` содержит единственную
  запись `pending_reboot` — эта прошивка не экспонирует ни кривых вентилятора,
  ни PPT-атрибутов. На обороты можно влиять только косвенно: меняя количество
  выделяемого тепла или выбирая другую кривую EC через `platform_profile`.
- **Андервольтинга нет.** Intel заблокировала его на Meteor Lake.
- **`asusctl` не проверялся.** Здесь не установлен; поддержка UX3405MA
  неизвестна.

## Профиль термополитики

- `/sys/firmware/acpi/platform_profile` — `quiet` / `balanced` / `performance`;
  набор подтверждается через `platform_profile_choices`.
- `/sys/devices/platform/asus-nb-wmi/throttle_thermal_policy` — 0 = balanced,
  1 = performance, 2 = quiet. Меняется синхронно с `platform_profile`.
- `system76-power profile balanced|performance` переключает оба без root.
  Значения `quiet` у него нет — только прямой записью в sysfs от root.

Это выбирает кривую вентилятора в EC и является единственным способом сдвинуть
кривую целиком. `quiet` заставляет EC терпеть больше тепла до раскрутки, то есть
меняет горячий корпус на более медленный вентилятор.

**Запись в `platform_profile` заставляет прошивку заново выставить свои лимиты
мощности.** Поэтому любые значения RAPL пишутся *после* профиля, а не до, и
перечитываются для проверки.

## Вентилятор

- Каталог hwmon: `/sys/devices/platform/asus-nb-wmi/hwmon/hwmon*/`. Номер
  `hwmon*` между загрузками не стабилен — разрешать по `name` (`asus`).
- `fan1_input` — обороты в RPM.
- `pwm1_enable` — `2` авто, `0` полная скорость. Требует root.
- Второе показание оборотов даёт hwmon `acpi_fan` (`fan1`) и служит
  перекрёстной проверкой.

Измеренное поведение, 12-минутная выборка с частотой 0.2 Гц при loadavg ≈0.6:

| | |
|---|---|
| Обороты в простое | 1900 RPM в 109 выборках из 144 |
| Наблюдавшийся диапазон | 1900–2500 в простое; 3200 под лёгкой нагрузкой; максимум 6100 |
| Порог раскрутки | выше самых низких оборотов при температуре пакета около 62 °C |

### 1900 RPM — это не нижняя граница

В короткой выборке выше остановки не встретилось ни разу, отчего 1900 RPM и
выглядели аппаратным минимумом. Две записанные сессии с частотой 1 Гц говорят
другое — 6019 выборок и 20 204 выборки, снятые с разницей в сутки:

| Пакет, °C | Доля выборок с `fan1_input` = 0 | Вентилятор p50 / p90, RPM |
|---|---|---|
| ниже 45 | 100 % | 0 / 0 |
| 45–48 | 29 % | 1700 / 1700 |
| 48–50 | 16 % | 1700 / 1900 |
| 50–52 | 3 % | 1900 / 2100 |
| 52–55 | 0.4 % | 2000 / 2000 |
| 55–60 | 0 % | 2000 / 2800 |
| выше 60 | 0 % | 3000 / 3700 |

Примерно ниже 45 °C EC останавливает вентилятор совсем, между 45 и 52 °C держит
его на грани, выше 55 °C не останавливает никогда. Ноль здесь — это показание, а
не пропуск: пропущенное показание записывается как отсутствующее и уходит в
экспорт пустым полем.

Для шумовой цели это лучше, чем нижняя граница, и это меняет то, чего можно
добиться настройкой простоя: запас оборотов всё-таки есть, но отдать его можно
только выделяя меньше тепла, то есть той же ручкой, что и раньше.

### Корпус и пакет идут вместе

В обеих сессиях показание `acpitz` и температура пакета сходятся с точностью до
градуса во всех полосах нагрузки, так что в сценарии «сижу за столом»
температура пакета честно описывает корпус. На ноутбук, лежащий на человеке, это
не переносится: путь отвода тепла другой, и сценарий, который судят по коже,
судят по `acpitz`.

## Мощность и частота процессора

- `/sys/devices/system/cpu/intel_pstate/no_turbo` — 1 выключает турбо.
- `/sys/devices/system/cpu/intel_pstate/max_perf_pct` — потолок частоты в
  процентах (`min_perf_pct` здесь 8).
- `/sys/devices/system/cpu/intel_pstate/hwp_dynamic_boost` — по умолчанию 1.
- `/sys/devices/system/cpu/cpu*/cpufreq/energy_performance_preference` —
  `default` / `performance` / `balance_performance` / `balance_power` / `power`.
  По умолчанию `balance_performance`.
- `scaling_driver` — `intel_pstate`, `scaling_governor` — `powersave`.

Вместе EPP по умолчанию и HWP dynamic boost позволяют процессору подниматься
почти до максимальной частоты ради пустяковой работы. Именно эти короткие
всплески греют пакет, когда машина номинально простаивает; лимит длительной
мощности в простое не достигается и потому на неё не влияет.

### RAPL

`/sys/class/powercap/intel-rapl:0/` (`name` = `package-0`):

| Узел | Смысл | Наблюдалось |
|---|---|---|
| `constraint_0_power_limit_uw` | PL1, long term, мкВт | 200 Вт в профиле `performance` от прошивки |
| `constraint_1_power_limit_uw` | PL2, short term, мкВт | 115 Вт |
| `constraint_2_power_limit_uw` | peak power | 217 Вт |
| `constraint_0_time_window_us` | окно усреднения PL1 | 31 981 568 мкс (≈32 с) |
| `constraint_1_time_window_us` | окно усреднения PL2 | 2440 мкс |
| `energy_uj` | счётчик энергии пакета, только root | переполняется на `max_energy_range_uj` |

Поддомены `intel-rapl:0:0` (`core`) и `intel-rapl:0:1` (`uncore`) несут
отдельные счётчики энергии, что позволяет отличить нагрев от CPU и от iGPU.

PL1 — самая действенная ручка для длительной нагрузки. Окно усреднения PL1
доступно на запись, и им редко пользуются: короткое окно даёт ровную мощность
вместо спринтов, что снижает пиковую температуру почти без заметной платы.

**PL1 в 200 Вт на ноутбуке, рассчитанном примерно на 28 Вт, — больше, чем
корпус способен рассеять.** Под длительной нагрузкой пакет может дойти до
аппаратного рубильника раньше, чем успеет отработать троттлинг; журнал ядра
тогда обрывается на полуслове без записи о завершении — это сигнатура
THERMTRIP, а не программного сбоя. Именно этот отказ проект и предотвращает.

## Встроенная видеокарта

Драйвер `i915`, экспонируется как `card1`. Видеозвонок нагружает графическое
ядро не меньше, чем процессорные — декодирование каждого удалённого потока,
кодирование своего и любая непрерывная инференция вроде автокадрирования, — и
**ни одна из процессорных ручек на это не влияет.** `max_perf_pct`, `no_turbo`
и EPP действуют только на ядра. Пакетный PL1 общий расход ограничивает, но у
графики есть и собственные ручки:

| Узел | Смысл | Наблюдалось |
|---|---|---|
| `/sys/class/drm/card*/gt_max_freq_mhz` | потолок частоты, пишется | 2350 |
| `/sys/class/drm/card*/gt_min_freq_mhz` | нижняя граница частоты | 100 |
| `/sys/class/drm/card*/gt_act_freq_mhz` | текущая частота | — |
| `/sys/class/drm/card*/gt_RP0_freq_mhz` | аппаратный максимум | 2350 |
| `/sys/class/drm/card*/gt_RPn_freq_mhz` | аппаратный минимум | 800 |
| `/sys/class/powercap/intel-rapl:0:1/constraint_0_power_limit_uw` | лимит мощности домена uncore | — |

**Нижняя граница для записи в `gt_max_freq_mhz` — это `gt_RPn_freq_mhz`, здесь
800, а не `gt_min_freq_mhz`.** Два узла легко спутать, и разница проявляется
молча: потолок ниже RPn отвергается сразу, узел сохраняет прежнее значение, и
сказать об этом может только чтение обратно. Измерено дорогой ценой — 3826
подряд идущих выборок с запрошенным потолком 100 все сообщали о расхождении
органа управления с демоном, и ни в одном из них потолок не был применён.

Вместе они позволяют ограничить графику, не трогая производительность
процессора, — что существенно, когда тепло идёт именно оттуда.

Медиадрайвер Intel (`iHD_drv_video.so`) установлен, то есть аппаратное
декодирование и кодирование видео на уровне системы доступны. Пользуется ли ими
конкретное приложение — отдельный вопрос: программное декодирование множества
одновременных видеопотоков дорого, и его вполне можно избежать.

### Разъёмы экранов

`/sys/class/drm/card1-<разъём>/status` отдаёт `connected` или `disconnected` по
каждому разъёму, без сессии и без графического сервера, — поэтому демон и может
их считать. Здесь наблюдаются: `eDP-1` для встроенной панели и `DP-1`, `DP-2`,
`HDMI-A-1` для внешних.

Число подключённых пишется в каждую выборку, потому что отрисовка внешнего
монитора — работа, которую нельзя отложить (потолок iGPU её не откладывает, а
только делает запоздалой), а её цена не видна в логе, который не говорит, был ли
монитор подключён.

Чего этот узел не знает: разъём числится подключённым, пока в нём кабель, горит
вывод или нет, а разветвитель DP-MST виден не так, как ожидается. Разрешения и
масштабирования там нет вовсе — разъём перечисляет поддерживаемые режимы, а
какой из них включён, знает композитор. И то и другое в любом случае было бы
косвенной оценкой объёма графической работы, а она уже измеряется напрямую —
доменом uncore в RAPL и `gt_act_freq_mhz`.

### Внешние мониторы отвечают по DDC/CI, внутренняя панель — нет

Яркости внешнего монитора в sysfs нет. Это разговор по шине I2C того разъёма, на
адресе 0x37 — DDC/CI, — а сама шина лежит в
`/sys/class/drm/card1-<разъём>/ddc` символьной ссылкой на тот `i2c-N`, по которому
идёт обмен. Замерено: `DP-1` — шина 12, `DP-2` — шина 13, и шина принадлежит
разъёму, а не монитору.

Замерено три монитора, все по VCP 0x10 и все с заявленным максимумом 100:

| Монитор | Разъём, шина | Серийник в EDID | Чтение | Запись, проверка библиотеки включена | Запись, выключена |
|---|---|---|---|---|---|
| `DELL U3425WE`, MCCS 2.1 | `DP-1`, `i2c-12` | `421B3Z3` | 353 мс | 405 мс, успех | 301 мс, успех |
| `RTK TYPEC`, MCCS 2.2 | `DP-2`, `i2c-13` | `L56051794302` | 351–357 мс | **1344 мс, DDCRC_RETRIES** | 302 мс, успех |
| `WCS AQ14T` | `DP-2`, `i2c-13` | нет, а в числовом поле `0x01010101` | 351–359 мс | 409 мс, успех | 300 мс, успех |

Отсюда четыре следствия, и все четыре сидят в коде:

- **Собственная проверка библиотеки ломает запись.** `ddcutil` читает значение
  обратно сразу, а одна из этих панелей так быстро ответить не готова: она отдаёт
  `DDCRC_RETRIES`, при том что записанное значение в мониторе уже стоит. С
  выключенной проверкой та же запись стоит 302 мс и сообщает об успехе — поэтому
  проверка выключена, а подтверждает запись ближайшее обычное чтение.
- **Код возврата записи — не ответ.** Ответ даёт чтение. Отказ выше замерен, а не
  придуман.
- **Кручение кнопками самого монитора видно.** Уровень, выставленный его
  собственными клавишами, читается по DDC, и именно поэтому модель «рука — это
  указание» работает для монитора так же, как для панели.
- **На серийник полагаться нельзя.** У одной панели строкового дескриптора нет
  вовсе, а в числовом поле заглушка, поэтому там, где серийника нет, в
  идентификатор идёт разъём.

Внутренняя панель сидит на шине 11 и отвечает `DDC communication failed`, прямо
говоря, что панель ноутбука DDC/CI не поддерживает. Она остаётся на
`intel_backlight`.

Два монитора подряд читаются 704–707 мс, то есть шины складываются, а не идут
параллельно, и весь обмен живёт в отдельном потоке: в цикле 1 Гц сидит аварийный
клапан, и он экран не ждёт.

`/dev/i2c-*` — `root:i2c 0660` плюс ACL на локального пользователя сеанса. Демон
работает от root, и добавлять ему ничего не нужно.

### Счётчики аппаратного троттлинга

`/sys/devices/system/cpu/cpu*/thermal_throttle/` — `core_throttle_count`,
`package_throttle_count`, `*_total_time_ms`, `*_max_time_ms`. Они считают
собственное аварийное срабатывание железа: растущий счётчик — прямой сигнал
«программные рамки не сработали». Счётчики кумулятивны в пределах загрузки,
поэтому осмысленна только скорость их роста.

## Батарея

`/sys/class/power_supply/BAT0/charge_control_end_threshold` существует и
доступен на запись, то есть ограничение заряда — операция над одним файлом.

## Сенсоры

| hwmon `name` | Что даёт |
|---|---|
| `coretemp` | `Package id 0` и температуры ядер; high = crit = 110 °C |
| `acpitz` | температура корпуса/платы |
| `nvme` | Composite и два сенсора; crit 84.8 °C |
| `iwlwifi_1` | температура Wi-Fi модуля |
| `BAT0` | мощность батареи |
| `asus` | обороты вентилятора |
| `acpi_fan` | обороты, второй источник |

Номера `hwmon*` между загрузками не стабильны. Разрешать каждый сенсор по
`name`.

## Датчик освещённости и подсветка

Оба существуют и не связаны ни с чем выше. Они описаны здесь потому, что демон
пишет подсветку, а не потому, что хоть один из них имеет отношение к теплу:
выбор теплового режима никогда не двигает подсветку.

| Узел | Значение |
|---|---|
| `/sys/bus/iio/devices/iio:device0/name` | `als` — только для опознания, см. ниже |
| `.../in_illuminance_raw` | растёт со светом; читается без root |
| `.../in_illuminance_scale` | `0.001000000` — сырые отсчёты идут тысячными долями люкса; узла может и не быть, тогда демон считает множитель равным единице |
| `.../in_illuminance_offset` | `0` — прибавляется к сырому отсчёту до умножения |
| `.../in_illuminance_sampling_frequency` | `10.0` |
| `/sys/class/backlight/intel_backlight/max_brightness` | 400 |
| `/sys/class/backlight/intel_backlight/brightness` | `root:root 0644` |

То, как демон ими пользуется, определяют два свойства.

**Показание — это люксы, и так говорит сам драйвер.** `(raw + offset) × scale`
— договор IIO для `in_illuminance`, и числа, которые получаются здесь, похожи на
то, как комната выглядит. Замерено на этой машине за один вечер:

| Комната | Люксы |
|---|---|
| темно, экран выключен | 0,3 |
| две настольные лампы и фоновая подсветка, люстра выключена | 25,9 |
| то же, люстра включена — четыре лампы по 1000 лм, ноутбук в углу экраном к ним | от 65,5 до 103,5 |
| велосипедная фара на 1800 лм примерно в 7 см от датчика | 20 855 |

Демон хранит показание в миллилюксах: внизу этого диапазона живёт тёмная
комната, а целые люксы не отличают 0,3 от 3. Кривая отклика настраивается в
люксах — и в файле настроек, и в командной строке — и калибруется по записанной
телеметрии.

Верхняя граница датчика не установлена. Ничего ярче велосипедной фары под рукой
не было, дневной сессии не записано, так что последняя точка кривой опирается на
наблюдённый диапазон, а не на измеренный предел.

**Подсветка доступна на запись только root.** Поэтому ею владеет демон, а трей
её не трогает: всё, что трей делает с подсветкой, идёт через демон. Писать в неё
может и любой другой процесс от root — потому демон помнит последний известный
ему уровень: показание, отличающееся от этой памяти, есть чужая запись, а на
практике этот «кто-то» — человек за клавишами яркости.

`iio-sensor-proxy` установлен, но не запущен, так что сейчас никто больше не
управляет подсветкой по датчику. Если бы он был запущен, он и этот демон стали
бы двумя владельцами одной ручки. Ради предотвращения ровно этого проект
и существует.

Номер iio-устройства стабилен не больше, чем номер `hwmon`. Демон находит датчик
по наличию канала освещённости, а не по номеру и не по `name`: драйверы
расходятся в том, что писать в `name`, а устройство с каналом освещённости есть
датчик света, как бы оно себя ни называло.

## Измеренное тепловое поведение

Снято на одной машине. Абсолютные значения зависят от состояния охлаждения
конкретного экземпляра; переносимая часть — соотношения между настройками.

Как снималось — потому что число без методики измерением не является: восемь
потоков в холостом цикле, на каждую комбинацию **90 с на установление** и затем
**90 с записи**, а между комбинациями машина остывала до **65 °C**, чтобы ни
одна не наследовала тепло предыдущей. Время установления выбрано не наугад:
постоянная времени радиатора — десятки секунд, и замер раньше меряет переходный
процесс, а не состояние. Комбинация прерывалась, если пакет доходил до 95 °C.
Числа для простоя получены той же процедурой с нулём нагрузочных потоков.

- Температура пакета устанавливается на **60–63 °C в простое** при loadavg ниже 1.
  Что при этой температуре делает вентилятор, сказано в таблице выше, а не здесь:
  в этих прогонах писались пакет и мощность, а обороты — только под нагрузкой.
- Переключение с вендорского профиля `balanced` на `battery` — потолок частоты
  со 100% до 50%, турбо выключено, кривая EC уходит в `quiet` — изменило
  температуру пакета примерно на градус и не изменило обороты. Два эффекта
  гасят друг друга: тепла выделяется меньше, но ленивая кривая ровно настолько
  же убирает продув. Подавление всплесков само по себе, таким образом, не даёт
  ничего.
- Вендорские профили не трогают RAPL вообще. Лимиты мощности, записанные
  вручную, переживают любое переключение профиля нетронутыми.

## Конфликты владения

- `system76-power` владеет сразу всеми тремя DBus-именами:
  `com.system76.PowerDaemon`, `net.hadess.PowerProfiles` и
  `org.freedesktop.UPower.PowerProfiles`. `power-profiles-daemon` не установлен,
  так что за двумя последними больше никто не конкурирует. Штатный файл политики
  уже разрешает любому процессу от root владеть ими, и ни одно из трёх имён не
  активируется через шину — активационных файлов в
  `/usr/share/dbus-1/system-services/` нет, — поэтому маскирование юнита
  передаёт владение чисто и вендорский демон по запросу не перезапустится.
- **Настоящее имя вендорского юнита — `com.system76.PowerDaemon.service`**;
  `system76-power.service` — объявленный им `Alias=`, и на диске алиас
  существует только как символьная ссылка на него. Маскирование алиаса заменяет
  эту ссылку и оставляет настоящий юнит включённым в `multi-user.target.wants`,
  так что вендорский демон вернётся при следующей загрузке. Всё, что его
  маскирует, размаскирует или объявляет с ним конфликт, обязано называть
  настоящий юнит.
- `system76-power` также выставляет яркость экрана при смене профиля.
- `thermald` запущен по умолчанию и самостоятельно пишет в RAPL и
  `intel_pstate`.
- `system76-scheduler` управляет приоритетами процессов и к теплу отношения не
  имеет.

Все записи в sysfs теряются при перезагрузке.

### Вендорский DBus-интерфейс

Забрать имя означает отвечать на весь интерфейс. По интроспекции на этой
машине `com.system76.PowerDaemon` — шестнадцать методов и два сигнала:

| Член | Сигнатура | Примечание |
|---|---|---|
| `Battery` / `Balanced` / `Performance` | `() → ()` | выбор профиля |
| `GetProfile` | `() → s` | |
| `GetChargeThresholds` | `() → (y, y)` | начало и конец в процентах |
| `SetChargeThresholds` | `((yy)) → ()` | |
| `GetChargeProfiles` | `() → a(sssyy)` | id, заголовок, описание, начало, конец |
| `GetGraphics` / `SetGraphics` | `() → s` / `(s) → ()` | |
| `GetGraphicsPower` / `SetGraphicsPower` | `() → b` / `(b) → ()` | |
| `AutoGraphicsPower` | `() → ()` | |
| `GetDefaultGraphics` | `() → s` | |
| `GetSwitchable` | `() → b` | |
| `GetDesktop` | `() → b` | |
| `GetExternalDisplaysRequireDgpu` | `() → b` | |
| `HotPlugDetect` | сигнал `(t)` | |
| `PowerProfileSwitch` | сигнал `(s)` | |

Одиннадцать из них — про переключение графики, которого эта машина не умеет:
дискретной видеокарты нет. Это константы, а не функциональность.

Словарь тут вендорский, а не стандартный: `GetProfile` и `PowerProfileSwitch`
говорят `Battery`, `Balanced` и `Performance` — с большой буквы. Написание
входит в контракт: аплет панели COSMIC сверяет ответ ровно с этими тремя
литералами и на чём-либо ещё падает, а упавший аплет уносит с панели индикатор
батареи вместе с меню профилей.

Стандартный интерфейс — `net.hadess.PowerProfiles` и его псевдоним
`org.freedesktop.UPower.PowerProfiles` — меньше: свойства `ActiveProfile`,
`Profiles`, `Actions`, `ActiveProfileHolds`, `PerformanceInhibited` и
`PerformanceDegraded`, методы `HoldProfile` и `ReleaseProfile`, сигнал
`ProfileReleased`. Он принимает ровно три имени профиля — `power-saver`,
`balanced` и `performance`.

## Диагностика

```bash
sensors                                              # температуры и обороты
journalctl -k -b -1 | grep -i therm                  # троттлинг в прошлой загрузке
journalctl --list-boots                              # найти оборванные сессии
cat /sys/firmware/acpi/platform_profile              # текущий профиль
grep . /sys/class/powercap/intel-rapl:0/constraint_*_power_limit_uw
grep . /sys/devices/platform/asus-nb-wmi/hwmon/hwmon*/fan1_input
busctl --system introspect com.system76.PowerDaemon /com/system76/PowerDaemon
```
