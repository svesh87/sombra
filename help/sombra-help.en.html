sombra

This machine can be hot and quiet or cool and loud, and the firmware offers no way to ask for the point in between. sombra is that point: a daemon that holds the machine inside a chosen thermal envelope and follows the ambient light sensor, and this window to choose an envelope and tune it.

The daemon owns the thermal controls alone — two programs writing the same controls produce whichever result wins the race. Everything in this window is a request to the daemon, and every control here also exists as a command: man sombra.

A mode is a set of numbers, not a name for a mood: the power limits, the frequency ceilings, turbo, the energy preference and which fan curve the firmware follows. There are three, from the coolest envelope to the widest, and the middle one is where the machine spends nearly all of its time. The desktop panel's three slots are these same three modes.

Moving a control applies it at once; only Save to writes it down. While what is running is not one of the saved modes, the mode selector is empty and the Status tab says so.

Status — what only reports

Nothing on this tab changes anything, except the three buttons at the bottom, which write a judgement into the telemetry.

Readings

Package °C
The processor package, from coretemp. This is the temperature every limit here exists to hold down, and the one the emergency guard watches.
Board °C
The mainboard sensor, acpitz. It lags the package by minutes and says what the chassis is doing rather than what a burst just did.
NVMe °C
The drive's composite sensor. Nothing here controls it; it is on screen because a warm drive shares a chassis with everything else.
Fan RPM
Measured, not requested. The firmware decides the speed from the curve and the temperature — no value can be written to it, which is the reason this project exists.
Load average
The kernel's one-minute figure, for reading the rest of the column against.
Package power W
What the package is drawing, from the RAPL energy counter. Compare it with the long-term limit on the Mode tab: sitting at the limit under load is the limit working.
Core power, Uncore power W
The same draw split in two. Uncore separates the graphics and the memory side from the cores, which is how you tell a hot screen from a hot compiler.
CPU frequency MHz
The mean over the online cores.
iGPU frequency MHz
The graphics frequency now. Read it against the iGPU ceiling on the Mode tab.

State

Applied
The setpoints actually in force this second, spelled out. While the guard is clamping, the controls on the Mode tab say what was asked for and this line says what is happening.
On mains / On battery
The power source. The daemon reacts to the transition, so this explains a change nobody made.
The controls have been moved
Live tuning is in force: what is running is not one of the saved modes. The mode selector is empty for the same reason. Save to or Revert ends it.
Emergency thermal guard engaged
The package is near the hardware cutout and power is clamped regardless of mode. This is a safety interlock, always active, and the one thing that will run the fan up without being asked.
A control read back a value the daemon did not write
Something else is writing the thermal controls. That is the arrangement this project exists to prevent, and it usually means the vendor daemon came back.
Some sensors could not be read
A reading is missing rather than zero. When the package temperature is among them, the daemon falls back to the coolest mode instead of guessing.

How is it working

Good, Too loud, Too slow
Each stamps that judgement onto the reading of this second, so an opinion made by ear stays attached to the numbers that produced it. This is what the mode numbers are later tuned from; sombra export reads them back.

Mode — pick one, move it, keep it

Mode
Pick one and every control below takes its saved numbers. Empty means what is running is not any of them. Each entry carries its own numbers on hover.
Apply this one at boot
Which mode the daemon applies when the machine starts.

Its numbers

Long-term limit 1–45 W
The power the processor may draw for as long as it likes — RAPL PL1. This is the control that decides how hot the machine gets under sustained load, and therefore how fast the fan ends up spinning. The ceiling here is the highest value confirmed on this machine, not the highest the firmware would accept: its own performance profile programs 200 W on a laptop rated for about 28.
Short-term limit 1–65 W
What it may draw in a burst of a few seconds — RAPL PL2. It decides how quick the machine feels rather than how warm it runs.
Frequency ceiling 8–100 %
How much of the processor's frequency range is available. A power limit already bounds sustained heat; this bounds the peak directly.
iGPU ceiling 800–2350 MHz
The graphics frequency ceiling. Lowering it saves power, but driving an external monitor is work the graphics cannot postpone — too low a ceiling shows as stutter. 800 is the hardware minimum; below it the driver refuses the write.
Energy preference
What the processor is told to prefer between saving energy and answering quickly. performance answers as fast as possible whatever it costs; balance_performance leans that way; balance_power leans towards saving; power saves wherever it can, and it is what suppresses the short bursts that heat the package while the machine is nominally idle. The words are the kernel's, because they are what goes into the settings file.
Fan
One control with four answers. Three are the curves the firmware carries, measured here at identical power under sustained load: quiet about 2900 RPM and above 84 °C, balanced about 3700 RPM and 80 °C, performance about 5000 RPM and 74 °C. maximum is not a curve — it is full speed, roughly 6100 RPM, whatever the temperature. At idle the choice makes no difference at all: below roughly 45 °C the firmware stops the fan outright, and up to about 52 °C it holds it on the edge of stopping, whichever curve is selected. The curve starts to matter only once the package is warm enough for the firmware to ramp.
Turbo
Whether the processor may go above its base frequency at all.
HWP dynamic boost
Whether the hardware may raise the frequency on its own when it thinks the work needs it. Together with the energy preference, this is the pair that decides how much the machine warms itself up while doing nothing.

Keep it

Save to
Writes the numbers above into the mode named beside the button. Until this is pressed, a moved control is applied and not saved, and a restart forgets it.
Revert
Back to the saved numbers of the mode in force, discarding what was moved.

Backlight — a separate function

Selecting a thermal mode never moves the backlight, and nothing about the backlight reaches the thermal side. All five sliders are per cent of the panel's own scale.

Adjust to the light in the room
Whether the backlight follows the ambient light sensor. Switching it on or off never moves the backlight by itself — a jump in brightness in answer to a toggle is the same defect as one in answer to a mode switch. It is off until switched on, and that choice survives a reboot.
Brightness
The backlight as it is right now. Moving it states what you want in this light, and the baseline below follows from it: the daemon takes the room's contribution of that moment back out. That is why the same light later returns the same brightness. Correcting it by the keyboard keys does the same thing.
Baseline
The level the automation works around. Moving it sets the baseline directly, which is what to reach for when the light in the room is not the light you are tuning for. Greyed out while the automation is off, because then it is a number nothing acts on.
Reaction to light
How far the room may move the backlight either way from the baseline, in percentage points. A reaction of 30 around a baseline of 80 % means a dark room may pull it to 50 % and a bright one push it to 100 %.
Never darker than
The floor. Nothing goes below it — not the automation, and not a slip of the hand either, because a screen driven into unreadable is a failure whoever did the driving.
Never brighter than
The ceiling, on the same terms. It is the whole scale until you move it, and it is what to reach for on a screen that is unpleasant at its own maximum.

The one backlight setting that is not on a slider is the curve, which turns a light reading in lux into a position from 0 to 100. It is calibrated from recorded telemetry rather than judged by eye, and it is edited from the command line: man sombra.

Settings — about the program rather than the machine

Appearance
Follow the desktop, Light or Dark, kept in the console's own settings file. Following the desktop usually means changing nothing: a desktop that manages Qt applications hands them its colours already, and the console re-reads them when the desktop switches theme at sunset. The window's title bar takes its colours when the window is created, so a change of scheme reaches the widgets at once and the bar at the next opening.
Autostart
Whether this console starts with the session. It writes one XDG autostart entry and nothing else — the entry is the state, which is what makes something switched off stay off. It takes effect at the next login, because that is when the session reads autostart entries.
Reset everything
Every mode definition and every backlight setting back to the values compiled into the daemon. It asks first. The console's own appearance and the autostart entry are not part of it: they are about the window, not about the machine.

Where to look further

The command line does everything this window does and more: man sombra. The daemon has its own page, man sombrad, and so has this console, man sombra-tray. The project's documents — what the hardware actually offers, and the reasoning behind every decision here — are at github.com/svesh87/sombra.
